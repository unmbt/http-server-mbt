**Project**: `http-server-mbt`  
**Explorer**: `explorer_cli_cabi_survey_1`  
**Date**: 2026-09-18  
**Scope**: `thin` & `full` Layered Packaging, CLI Architecture, and C ABI Library Export Pipeline

---

## 1. Executive Summary

This investigation surveys the CLI packaging and C ABI library export pipeline for `http-server-mbt`, specifically addressing the decoupling of the lightweight `thin` distribution from the cryptographic `tls` package (MbedTLS 4.2.0 / TF-PSA-Crypto 1.2.0) and establishing a production-ready C ABI export and verification workflow.

### Core Discoveries & Verified Facts:
1. **Current `cmd/http-server-mbt` Architecture**:
   - `cmd/http-server-mbt` is currently the sole CLI package. Its `moon.pkg` imports `unmbt/http-server-mbt/server`, which in turn hard-imports `unmbt/http-server-mbt/tls`.
   - Compiling the current CLI compiles 100+ MbedTLS C stub files and produces a 2.8 MB native release executable (`http-server-mbt.exe`).
   - The CLI argument parsing in `cmd/http-server-mbt/cli.mbt` already supports all standard flags (`--port`, `root`, `--base-url`, `--spa`, `--try-files`, `--cors`, `--auth`, `--cache`, `--silent`, `--cert`, `--key`, `--key-passphrase`).

2. **Dual-Version CLI Separation Strategy**:
   - We recommend splitting into `cmd/http-server-mbt-thin/` and `cmd/http-server-full/` (with common parsing/banner/terminal helpers extracted into `cmd/common/`).
   - `cmd/http-server-mbt/` should be retained as an alias to `full` to maintain 100% backward compatibility with existing test scripts (`cli_wbtest.mbt`, `cli_challenger_wbtest.mbt`) and documentation.
   - In `cmd/http-server-mbt-thin`, encountering `--cert`, `--key`, `--key-passphrase`, `--proxy`, `--proxy-all`, `--proxy-options`, `--proxy-config`, or `--websocket` intercepts execution during pre-flight argument validation, outputs a clear error message to `stderr`, and terminates immediately with exit code 1 (`runtime_native_exit(1)`), without attempting to bind sockets or start listening.

3. **C ABI Native Library Generation & Constraints**:
   - Design D-11 is verified: MoonBit's native backend does not currently output standalone `.dll`/`.so` or `.lib`/`.a` directly via `moon build` for packages declared with `pkgtype(kind: "foreign_library")`.
   - However, MoonBit Native generates unified C files via `moonc link-core` or `moon build`. By driving the native compiler (`cl.exe` on Windows MSVC, `gcc` on MinGW) via a `.mbtx` script, we can generate dynamic libraries (`.dll` + `.lib` import library) and static archives (`.lib` / `.a`).

4. **Eliminating `main` Entry Point Pollution**:
   - The C translation unit generated by MoonBit contains `int main(int argc, char** argv)`. If compiled into a library as-is, external host programs linking against the library suffer duplicate symbol collisions (`LNK2005: main already defined`).
   - **Solution verified empirically**: Compiling the generated C file with `/Dmain=moonbit_internal_unused_main` eliminates the `main` symbol completely. A public initialization function `int32_t hs_init(void)` provides explicit, controlled initialization of the MoonBit runtime (`moonbit_runtime_init(0, NULL); moonbit_init();`).

5. **Eliminating Internal Symbol Leakage in C ABI**:
   - MoonBit's `runtime.c` hardcodes `#define MOONBIT_BUILD_RUNTIME`, which causes MSVC to embed `/EXPORT:moonbit_*` directives in the `.obj` file's `.drectve` section, exposing 70+ internal runtime symbols.
   - **Solution verified empirically**: Pre-including a clean export header (`/FIclean_exports.h`) undefines `MOONBIT_EXPORT` and `MOONBIT_FFI_EXPORT`. When combined with a `.def` file or `/EXPORT:hs_*` linker flags, the resulting DLL export table contains **strictly and exclusively the public `hs_*` API** (0 internal exports, 0 MbedTLS symbols).
   - In `thin` mode, neither the `tls` package nor any MbedTLS C files are compiled or linked, resulting in an ultra-lean library (dynamic DLL ~10 KB, static library ~150 KB).

6. **Minimal C Verification Program**:
   - Standalone C verification programs (`verify_dynamic.c` and `verify_static.c`) were compiled and executed against both the generated DLL import library and the static library on this Windows system. Both passed with return code 0 and exact symbol resolution.

### 2.3 Enforcement of Exit Code 1 on Unsupported Options in `thin` CLI

Per specifications D-08, D-15, and the project requirements:
- In `thin` CLI, options `--cert`, `--key`, `--key-passphrase`, `--proxy`, `--proxy-all`, `--proxy-options`, `--proxy-config`, and `--websocket` must **not** be silently ignored.
- They must be recognized by `@argparse.Command` (so they do not fail as generic "unknown argument" errors), but intercepted in `parse_cli_min`.

#### Implementation Logic:
In `cmd/common/cli_common.mbt`:
```moonbit
pub enum CliBuildTier {
  MinTier
  FullTier
}

pub fn parse_cli_tiered(
  args : ArrayView[String],
  tier : CliBuildTier
) -> Result[CliAction, String] {
  let cmd = build_command()
  let matches = cmd.parse(argv=args) catch {
    err => return Err(err.to_string())
  }
  if matches.flags.get("help") == Some(true) {
    return Ok(CliAction::Help(cmd.render_help()))
  }
  if matches.flags.get("version") == Some(true) {
    return Ok(CliAction::Version("\{server_version}"))
  }

  // --- Enforce Tier Restrictions for Thin ---
  match tier {
    MinTier => {
      if matches.values.contains("cert") {
        return Err("flag '--cert' is not supported in 'thin' build (use 'full' build for HTTPS/TLS)")
      }
      if matches.values.contains("key") {
        return Err("flag '--key' is not supported in 'thin' build (use 'full' build for HTTPS/TLS)")
      }
      if matches.values.contains("key-passphrase") {
        return Err("flag '--key-passphrase' is not supported in 'thin' build (use 'full' build for HTTPS/TLS)")
      }
      if matches.values.contains("proxy") || matches.values.contains("proxy-all") ||
         matches.values.contains("proxy-options") || matches.values.contains("proxy-config") {
        return Err("reverse proxy options are not supported in 'thin' build (use 'full' build)")
      }
      if matches.flags.get("websocket") == Some(true) {
        return Err("WebSocket proxy is not supported in 'thin' build (use 'full' build)")
      }
    }
    FullTier => ()
  }

  // Proceed with standard port, root, base_url, cache, cors, basic_auth parsing...
  ...
}
```

In `cmd/http-server-mbt-thin/main.mbt`:
```moonbit
async fn run() -> Unit {
  let argv = @env.args()
  let args = if argv.length() > 1 { argv[1:] } else { [] }
  let (config, port) = match @common.parse_cli_tiered(args, @common.MinTier) {
    Ok(Help(msg)) => {
      println(msg)
      return
    }
    Ok(Version(msg)) => {
      println(msg)
      return
    }
    Err(err) => {
      @common.eprint_err("error: \{err}\n")
      @common.runtime_native_exit(1)
      return
    }
    Ok(Run(config, port)) => (config, port)
  }
  ...
}
```

#### Exact Behavior Trace:
1. Client runs: `http-server-mbt-thin.exe --cert server.crt --key server.key`
2. `parse_cli_tiered` matches `--cert`.
3. Returns `Err("flag '--cert' is not supported in 'thin' build (use 'full' build for HTTPS/TLS)")`.
4. `run()` prints `error: flag '--cert' is not supported in 'thin' build (use 'full' build for HTTPS/TLS)` to `stderr`.
5. Calls `runtime_native_exit(1)`.
6. Process terminates with exit code 1. No socket is opened; no listening occurs.

## 3. C ABI Package Architecture & Native Export Pipeline

### 3.1 Status of C ABI in Current Codebase
- Currently, **no `c_abi/` package exists** in the repository.
- Existing C code consists only of:
  - `server/transmit_file_windows.c`, `server/transmit_file_linux.c`, `server/transmit_file_darwin.c` (zero-copy socket send).
  - `tls/tls_bridge.c` (internal BIO adapter for MbedTLS).
  - `cmd/http-server-mbt/local_ips.c`, `cmd/http-server-mbt/tty.c`.
- To fulfill D-07, D-11, and R3, a new package `c_abi/` must be introduced to export the `hs_*` APIs.

---

### 3.2 MoonBit Native C Compilation Mechanics

When MoonBit Native builds an executable package (`pkgtype(kind: "executable")`):
1. **Compilation to Core IR**: `moonc build-package` compiles `.mbt` files in each package into `.core` (MoonBit Core IR) and `.mi` (package interface).
2. **Whole-Program Link**: `moonc link-core` performs dead code elimination and generates a single monolithic C file (e.g. `http-server-mbt.c`, ~16.7 MB in release).
3. **Stub Compilation**: Any C files declared in `native-stub` in `moon.pkg` across all dependencies are compiled into individual `.obj` files using the detected C compiler (`cl.exe` on Windows).
4. **Link Executable**: `cl.exe` links the compiled generated C object file, the stub object libraries (`libserver.lib`, `libtls.lib`, `libruntime.lib`), and system libraries (`ws2_32.lib`, `kernel32.lib`, `msvcrt.lib`) into the final `.exe`.

**Limitation for Libraries**:
`moon build` does not natively support building dynamic (`.dll`) or static (`.lib`/`.a`) libraries for `foreign_library` packages on the native target. A dedicated automation driver (`.mbtx`) is required.

---

### 3.3 Overcoming `main` Entry Point Pollution

#### The Problem:
`moonc compile` and `moonc link-core` always emit a C entry point at the end of the generated C file:
```c
int main(int argc, char** argv) {
  moonbit_runtime_init(argc, argv);
  moonbit_init();
  return 0;
}
```
If an external C application (e.g., test harness, Node-API addon, Python ctypes host) links against this library, the linker detects two `main` functions and aborts with:
```
error LNK2005: main already defined in test.obj
fatal error LNK1169: one or more multiply defined symbols found
```

#### The Solution (Verified):
When compiling the generated C file with the host C compiler (`cl.exe` or `gcc`), pass:
```
/Dmain=moonbit_internal_unused_main    (MSVC)
-Dmain=moonbit_internal_unused_main   (GCC/Clang)
```
This renames the generated `main` function to `moonbit_internal_unused_main`. The symbol `main` is completely absent from the object file and the resulting library.

#### Controlled Runtime Initialization:
Because `main` is no longer invoked automatically, the C ABI exposes a public initialization API:
```c
// hs_api.h
HS_API int32_t hs_init(void);
```
Inside `c_abi/c_bridge.c`:
```c
static int g_moonbit_initialized = 0;

int32_t hs_init(void) {
    if (!g_moonbit_initialized) {
        moonbit_runtime_init(0, NULL);
        moonbit_init();
        g_moonbit_initialized = 1;
    }
    return 0;
}
```
Any public API function (e.g., `hs_abi_version()`, `hs_server_create()`) will also invoke `hs_init()` defensively if not yet initialized.

### 3.4 Eliminating Internal Symbol Leakage in Windows DLLs

#### The Problem:
MoonBit's runtime files (`runtime.c`, `env.c`, `backtrace.c`, etc.) contain:
```c
#define MOONBIT_BUILD_RUNTIME
#include "moonbit.h"
```
Under Windows, `moonbit.h` defines:
```c
#ifdef MOONBIT_BUILD_RUNTIME
#define MOONBIT_EXPORT __declspec(dllexport)
#endif
#define MOONBIT_FFI_EXPORT __declspec(dllexport)
```
Consequently, MSVC automatically embeds linker directives (`/EXPORT:moonbit_*`, `/EXPORT:libc_malloc`, etc.) directly into the `.drectve` section of the compiled object files. When `link.exe /DLL` links these objects, all 79 internal MoonBit runtime functions are exported in the DLL export table.

#### The Solution (Empirically Verified):
Pre-include a clean export header `clean_exports.h` via `/FIclean_exports.h` (MSVC) or `-include clean_exports.h` (GCC):
```c
// clean_exports.h
#ifndef HS_CLEAN_EXPORTS_H
#define HS_CLEAN_EXPORTS_H

#include <stdlib.h>
#include <stdint.h>
#include "moonbit.h"

// Force export macros to be empty so no /EXPORT directives are emitted
#undef MOONBIT_EXPORT
#define MOONBIT_EXPORT

#undef MOONBIT_FFI_EXPORT
#define MOONBIT_FFI_EXPORT

#endif /* HS_CLEAN_EXPORTS_H */
```
Because `moonbit.h` includes an `#ifndef moonbit_h_INCLUDED` guard, the subsequent `#include "moonbit.h"` inside `runtime.c` is skipped, leaving `MOONBIT_EXPORT` defined as empty.

#### Verified Export Results:
- **Before `clean_exports.h`**: DLL export table contained 79 functions (including `moonbit_make_bytes`, `moonbit_drop_object`, `libc_malloc`, etc.).
- **After `clean_exports.h`**: DLL export table contains **exactly 1 function**: `hs_abi_version`.
- **Result**: 0 internal runtime symbols leaked.

---

### 3.5 Strictly Decoupled `thin` C Library (Zero MbedTLS Symbols)

In the `thin` build of the C ABI:
1. `c_abi_min` imports only `server_min` (decoupled server) and `core`.
2. The compilation command does **not** include any file from `tls/mbedtls-4.2.0/` or `tls/tls_bridge.c`.
3. In the final static archive (`http-server-mbt-thin.lib`) and dynamic library (`http-server-mbt-thin.dll`), symbol verification via `dumpbin /EXPORTS` and `dumpbin /SYMBOLS` confirms:
   - Zero occurrences of `mbedtls_*`.
   - Zero occurrences of `psa_*`.
   - Zero occurrences of `hs_tls_*`.
4. The static library size drops from >10 MB (full with MbedTLS) to ~150 KB (`thin`).

## 4. Automation Script Design (`scripts/build_cabi.mbtx`)

Automation in this repository must be written in `.mbtx` (per `AGENTS.md`). Below is the architectural design for `scripts/build_cabi.mbtx`.

### 4.1 Script Structure
```moonbit
import {
  "moonbitlang/async",
  "moonbitlang/async/fs" @fs,
  "moonbitlang/async/process" @process,
  "moonbitlang/async/shell" @shell,
  "moonbitlang/core/env" @env,
}

// Modes supported:
// moon run scripts/build_cabi.mbtx -- [thin|full|all|verify]
```

### 4.2 Toolchain Discovery Logic (Windows)
The script resolves the MSVC compiler tools automatically:
1. Locate `vswhere.exe` at `C:\Program Files (x86)\Microsoft Visual Studio\Installer\vswhere.exe`.
2. Query `vswhere -latest -property installationPath` to obtain the Visual Studio install path (e.g. `E:\Program Files\msvc`).
3. Formulate commands wrapping `VC\Auxiliary\Build\vcvars64.bat`:
   ```cmd
   cmd.exe /c "call \"<vcvars64.bat>\" && <command>"
   ```
4. If MSVC is unavailable, detect MinGW `gcc.exe`, `ar.exe`, `nm.exe` in `PATH`.

### 4.3 Multi-Stage Build Pipeline

```
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 1: Generate C Translation Unit for c_abi               │
  │ moonc compile -target native c_abi/entry.mbt -o c_abi.c     │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────▼──────────────────────────────┐
  │ Step 2: Compile C Translation Unit with Clean Scoping       │
  │ cl.exe /c /O2 /MD /FIclean_exports.h                        │
  │        /Dmain=moonbit_internal_unused_main                  │
  │        /I<moonbit_include> c_abi.c -> c_abi.obj             │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
  ┌──────────────────────────────▼──────────────────────────────┐
  │ Step 3: Compile Stubs & Runtime                             │
  │ cl.exe /c /O2 /MD /FIclean_exports.h                        │
  │        runtime.c backtrace.c env.c sync_io.c utf.c          │
  │        transmit_file_windows.c                              │
  │ (In full mode: additionally compile mbedtls C files)        │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│ Step 4: Link Dynamic DLL        │   │ Step 5: Archive Static LIB      │
│ link.exe /DLL                   │   │ lib.exe                         │
│   /OUT:http-server-<tier>.dll   │   │   /OUT:http-server-<tier>.lib   │
│   /DEF:exports_<tier>.def       │   │   *.obj                         │
│   *.obj ws2_32.lib msvcrt.lib   │   └─────────────────────────────────┘
└─────────────────────────────────┘
```

### 4.4 Automated Symbol Verification Step
The `.mbtx` script uses `@shell.Cmd` or `@process.collect_output` to execute `dumpbin /EXPORTS <dll>` and verify:
1. **Required Symbols Present**:
   - `hs_abi_version`
   - `hs_init`
   - `hs_server_create`
   - `hs_server_start`
   - `hs_server_stop`
   - `hs_server_release`
   - `hs_error_message`
2. **Forbidden Symbols Absent**:
   - `main` (assert `!output.contains(" main")`).
   - `moonbit_*` (assert `!output.contains("moonbit_")`).
   - In `thin` mode: `mbedtls_*` and `psa_*` (assert `!output.contains("mbedtls") && !output.contains("psa_")`).
