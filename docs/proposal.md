## 2. 目标、使用者与产品形态

服务开发者可以用 CLI 托管静态站点、预览 SPA 或使用原版代理功能；MoonBit 应用可以复用静态引擎与中间件；其他语言宿主可以通过 C ABI 嵌入同一引擎。

两种使用方式均默认由库托管事件循环：完整服务模式中，宿主传入配置、启动及停止服务；静态库模式中，宿主提交请求并将异步响应接入已有 HTTP 框架，库负责静态解析、缓存/Range、文件读取及异步操作。宿主无需手动推进、等待或唤醒事件循环，公开 pump/run/poll 下沉为内部机制。

最终形态包括：三平台 Native CLI、可通过 Mooncakes 引入的 MoonBit 静态文件库/中间件、Linux 完全静态 ELF、Distroless thin/full Docker 镜像及对应 `scratch` 变体、C 头文件和静态/动态库、Node-API `.node` 插件及 npm 适配包，以及实验性 wasm-gc 引擎与宿主适配示例。C 动态库为 Linux `.so`、macOS `.dylib`、Windows `.dll`；静态库为 `.a` 或 MSVC `.lib`，不是 Rust 专用 `.rlib`。

C/Python 动态库示例继续保留，新增 C/Rust 静态链接消费验证和正式 Node 适配。Bun/Deno 的 Node-API 兼容性及 Go/Rust/C++ 的完整 SDK 不自动列入正式支持；Rust 本次提供最小消费示例，ABI 可供后续适配。Node 插件默认静态链接同一引擎，不另行复制静态文件业务实现。

Linux、macOS、Windows 的最终功能和验收要求同等，开发顺序先从 Windows 本机开始：先跑固定原版基线，再完成 Native 静态请求与 IOCP/TransmitFile 零拷贝路径，随后在 GitHub Actions 逐步跑通三平台全部适用功能、测试和打包。本机阶段不等待所有平台或库导出实验完成，也不因 Windows 通过而宣称三平台完成；具体阶段依赖见 D-16。

Native 为生产服务器后端；wasm-gc 为需要宿主提供文件/计时/网络能力的实验引擎，单独验收。Mooncakes 的 Native 静态文件 API 必须可直接被其他 MoonBit 模块引入，不能要求调用 CLI 子进程或通过 C ABI 绕行；可移植核心另提供 Native/wasm-gc 包入口。Docker 初始产物为 Linux amd64 镜像，在 Linux Actions runner 验证；三平台支持不等于提供 Windows/macOS 容器镜像。

### 3.1 原版兼容边界

完整兼容包覆盖静态文件、默认扩展名、目录索引/列表、MIME 与字符集、ETag/条件请求、Range、预压缩、错误委托、配置别名、自定义头、Basic Auth、Host 白名单、CORS/COOP/PNA、robots、IPv4/IPv6、端口/超时/CLI、HTTP/HTTPS 代理、规则重写和 WebSocket 转发。

兼容指可观察的行为，不要求复刻 Union 的嵌套回调、Node 对象布局、Express 安装依赖或原 JS 测试加载方式。原版表达式中的正文、状态码、响应头、错误委托和生命周期含义必须保留；`server.listeners(...)` 等 Node 细节转为对应能力/事件测试。测试本身存在的缺陷、平台跳过以及本设计已确定的新行为见 D-01 的差异记录，不得隐藏为“全部原版断言原样通过”。

### 3.2 独立路由特性

BaseURL 是 URL 路径挂载前缀，不是完整站点地址，也不自动改写 HTML/JS 中的绝对资源路径。默认 `/`，可单独使用；保留 `--base-dir` 别名。

`--spa` 使用根目录下 `index.html`；`--try-files xxx.html` 指定单个回退文件。两者互斥，也与启用的代理配置互斥。所有未命中的 GET/HEAD 都可回退，包括缺失的 JS/CSS 和 API 路径，不按 Accept 或扩展名筛选。认证、路径或权限错误不能回退。完整优先级、文件删除行为和参数组合见 D-04。

## 4. 高性能原则与可行性边界

保证高性能，先把单进程 I/O、事件调度和静态处理做好；保留背压、资源限额、减少复制/分配及高效目录算法。本轮不规定量化的连接规模、启动时延、控制块/产物体积或提升倍率，不要求专项性能报告或新增监控产品。原 P 编号与 T-024 仅作为已撤出范围的历史记录保留，不参与当前完成门槛；资源回收、调度公平性和实际内核传输仍作为功能正确性验证。

内核文件传输主要适用于明文、已存在的静态文件。TLS、动态目录页、宿主不接受原生文件传输的嵌入模式使用有界缓冲；一般 TLS 不宣称 sendfile 零拷贝。StringBuilder 会涉及存储、扩容和最终字符串分配，优化目标是减少临时对象和重复复制，不是“天然无堆分配”。

Linux CLI 使用 musl 静态链接并验证无动态解释器/共享库需求。macOS 独立程序保留系统动态库，Windows 保留系统 DLL。三平台独立 CLI 均不依赖用户安装 MoonBit、Node、Python 或额外 TLS 运行库；Node/Python 示例需要对应宿主，wasm-gc 需要 WasmGC 宿主，Mooncakes 源码包需要 MoonBit 构建工具链，分别记录各形态依赖。

本地 async 的 Unix TLS 实现按需动态加载 OpenSSL，不能直接满足完全静态分发。设计采用随构建静态链接的 TLS 依赖，必须验证证书、加密私钥、代理和错误处理；不能自制密码学以追求体积。现有 async 的 continuation、调度对象和平台 I/O 可以作为调研材料，不修改 `.mooncakes/` 内的缓存来实现生产功能。

库产物另有工具链前置条件：此次查阅的 [MoonBit 官方 FFI 文档](https://docs.moonbitlang.com/en/latest/language/ffi.html#export-functions)明确提示 Native 尚不能直接把 `foreign_library` 输出为可链接库。该在线说明不能替代本机 `moon 0.1.20260824` 的实际验证。T-002 必须先验证生成 C、导出桥接、runtime 初始化和外部编译/归档/链接链路；未验证前不能宣称 `moon build` 已可直接生成正式 `.a`/`.so`/`.node`。静态库可链接也不等于最终应用完全静态。

wasm-gc 必须由支持 WasmGC 的宿主运行，文件/网络通过显式导入或适配器提供；当前 async 的 wasm-gc 事件循环存在未实现路径，不能直接复用 Native runtime。Mooncakes 发布的是可被 MoonBit 编译器消费的模块源码及必要构建资源，与分发预编译 C 库、npm 插件是不同渠道。

## 5. 交付顺序与完成定义

1. 在 Windows 本机固定测试资产及差异、运行原版基线，完成 Windows Native 必需探针；库导出等独立可行性实验分别推进。
2. 建立配置、HTTP、路径安全及静态引擎，先跑通 Windows IOCP/TransmitFile 的真实 HTTP 传输，复用到后续生产代码。
3. 接入 GitHub Actions 三平台基础矩阵，复跑原版基线与已迁移案例，补齐 Linux/macOS 探针，逐步完成 TLS、代理、WebSocket及中间件。
4. 在三平台工作流完成无栈事件循环、内核文件传输和目录优化的共同验收；Windows 本机继续提供日常快速反馈。
5. 完成 BaseURL、SPA、自定义回退及参数冲突测试。
6. 通过 GitHub Actions 完成静态/动态库、C/Python/Rust 消费验证、Node-API、Mooncakes 候选包、独立程序、Distroless/scratch thin/full 镜像打包，补齐实验 io_uring/wasm-gc、托管生命周期、文件变更、故障注入/模糊测试及全量兼容工作流。

每阶段交付必须能独立验证，实验实现不能冒充生产后端。完整重构的功能完成条件是三平台 Native 共同能力、全部适用迁移用例、新增契约测试、资源/分发检查、库/Node/Mooncakes 消费验证及实验 wasm-gc 声明范围内的验证均通过，并有对应提交的 GitHub Actions 运行、产物及报告；各形态的适用范围与差异需在报告中可见。实际镜像仓库/registry/npm 发布不是本次文档操作，发布成功与候选包可消费须分开记录。

本次文档完成条件是：四文件一致、R-N01～R-N16 均可追踪、42 个测试文件及实际参数化案例均有归属、托管生命周期/文件变更/故障注入契约明确、原量化性能计划已撤出且不阻塞当前任务、全部未来任务未勾选。保持已有路由、分发及 Windows→Actions 路线，不以文档交付声称功能已实现。
